Inception

A small web infrastructure built from scratch with Docker Compose: nine services, each in its own container, built from our own Dockerfiles on Alpine Linux. NGINX is the only way to the web services, over HTTPS with TLS 1.2 / 1.3 only. The bonus FTP server is the one other door in.

https://rapoggi.42.fr

Architecture

Two services are published to the host: NGINX on 443, and FTP on 21 plus its passive range 21000-21010. Everything else is reachable only on the private Docker bridge network.

Routing

How NGINX maps each public path to a backend.

PathGoes toHow
/wordpressFastCGI to wordpress:9000
/wp-admin/wordpressWordPress administration panel
/adminer.phpadminerFastCGI to adminer:9000
/site/siteHTTP proxy to site:80 — this page
/api/chatHTTP proxy to chat:5000

Ollama is deliberately not routed. The model server is reachable only from the chat API inside the Docker network, so nobody from outside can pull, delete or query models directly.

Services

Nine containers, nine Dockerfiles, all built from the same pinned Alpine base.

nginx

MANDATORY

alpine + nginx · port 443 (published)

The only way into the web services. It terminates TLS with a self-signed certificate generated on first start, serves WordPress static files straight from the shared volume, and forwards everything else to the right backend. TLS 1.0 and 1.1 are refused.

Check the TLS version

openssl s_client -connect rapoggi.42.fr:443 -tls1_2
openssl s_client -connect rapoggi.42.fr:443 -tls1_1   # fails

wordpress

MANDATORY

alpine + php-fpm 8.3 + WP-CLI · port 9000

WordPress running under php-fpm, with no web server of its own: NGINX cannot execute PHP, so it hands .php requests over FastCGI. The first start downloads WordPress, writes the config, and creates an administrator plus a second author account.

List the WordPress users

docker compose exec wordpress \
  wp user list --path=/var/www/html --allow-root

mariadb

MANDATORY

alpine + mariadb · port 3306

The database behind WordPress. It initialises itself on first start: it creates the database and the application user, sets the root password from a Docker secret, and drops the anonymous accounts. The root account stays restricted to localhost.

Open a SQL shell

docker compose exec mariadb \
  mariadb -u wpuser -p wordpress

redis

BONUS

alpine + redis · port 6379

A persistent object cache for WordPress. By default WordPress caches database results only for the duration of a single request; the Redis drop-in keeps them between requests, so repeated queries never reach MariaDB. Nothing is written to disk — it is a pure cache, capped at 64 MB with LRU eviction.

Confirm the cache is live

docker compose exec wordpress \
  wp redis status --path=/var/www/html --allow-root
docker compose exec redis redis-cli dbsize

ftp

BONUS

alpine + vsftpd · ports 21, 21000-21010

Read and write access to the WordPress files and to this static site, for editing content without rebuilding an image. The login is chrooted and runs as the same user that owns the web files, so uploads are immediately usable. Passive mode is used, since the data connection has to be opened by the client through Docker's NAT.

List both volumes over FTP

ftp 127.0.0.1
# or:
curl --disable-epsv -u ftpuser ftp://127.0.0.1/

adminer

BONUS

alpine + php-fpm 8.3 · port 9000

A single-file database manager for browsing tables, running queries and exporting data. Like WordPress it is pure PHP with no web server, so NGINX reaches it over FastCGI. It connects to MariaDB over the Docker network as the application user.

Log in at /adminer.php

System:   MySQL
Server:   mariadb
Username: wpuser
Database: wordpress

site

BONUS

alpine + nginx · port 80

The static showcase you are reading. Plain HTML and CSS, no PHP and no JavaScript framework, served by a minimal second NGINX. Its files live in their own volume, so they can be replaced over FTP without touching the image.

Publish a new page

curl --disable-epsv -u ftpuser -T index.html \
  ftp://127.0.0.1/site_data/index.html

ollama

BONUS

alpine + ollama · port 11434 (internal only)

A local language-model server. Models are stored in a dedicated volume so they survive rebuilds, and they are pulled on demand with a Makefile target rather than at container start. Everything runs on the CPU, inside the VM: no prompt ever leaves the machine.

Pull and list models

make pull-model
docker compose exec ollama ollama list

chat

BONUS

alpine + Flask on gunicorn · port 5000

A small HTTP API in front of Ollama, and the only component allowed to talk to it. Running under gunicorn rather than the Flask development server gives it a supervising master process, several workers and proper signal handling.

Ask the model a question

curl -k https://rapoggi.42.fr/api/ping

curl -k -X POST https://rapoggi.42.fr/api/chat \
  -d 'message=Explain Docker volumes in one sentence'

Data and persistence

Four Docker named volumes, stored on the host so the data outlives the containers.

VolumeUsed byContentsHost path
db_datamariadbThe WordPress database~/data/mariadb
wp_datawordpress, nginx, ftpWordPress files and uploads~/data/wordpress
site_datasite, ftpThis static site~/data/site
ollama_dataollamaDownloaded models~/data/ollama

These stay Docker named volumes, not bind mounts. The local driver is given type: none, o: bind and a device path, which is what puts their data under /home/<login>/data while Docker keeps managing them.

Running it

Everything goes through the Makefile at the root of the repository.

CommandWhat it does
makeGenerate missing secrets, create the data directories, build and start
make pull-modelDownload the language model into the Ollama volume
make downStop and remove the containers, keeping all data
make cleanAlso remove the volumes and the built images
make fcleanAlso delete the data directory — everything is lost
make refclean then a full rebuild
Built for the 42 curriculum. Replace rapoggi with your own login in every command and URL on this page.
